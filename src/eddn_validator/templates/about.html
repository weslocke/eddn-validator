How scoring works

Every message on the public EDDN relay has already passed EDDN's own format check. This site looks at what that check cannot see: whether an application follows the rest of EDDN's written rules, and whether its data agrees with what four long-established senders report.

The trusted reference apps

E:D Market Connector (Windows and Linux), EDDiscovery, EDDLite and EDO Materials Helper, the "big four". Only each one's three newest releases count. They don't always agree with each other, so "expected" means every reference app that sends that kind of message does it.

Five layers, in plain English

Each kind of message an app sends is scored on five layers. Each layer has its own page with the full list of what it checks.

  • Pairing: when an app reports a system, body or station, is it the same as what the big four reported about that same place? Only details that never change are compared (name, position, mass, orbit and so on), not things like distance that differ for every player. Compared with: the reference record for the same object, one message at a time. Six reports about the same body are six comparisons ("5 matched, 1 disagree").
  • Rules: does each message follow the rules EDDN and EDCD have written down? Does it break or bend any of them? Compared with: EDDN's documentation, each message on its own.
  • Fields: which fields does the app send? Does it leave out fields all of the big four send, or add fields none of them send? Compared with: how often the big four include each field in this kind of message.
  • Values: do the contents look right? This compares with a statistical profile of what the big four send in each field, a profile that shifts over time. Being a bit out of range is no big deal, since the galaxy has plenty of rare extremes: it's shown as a note and not counted. Only clearly wrong values count: the wrong kind of value, or something way out of line, like a units mistake. Compared with: the big four's overall profile for that field, not specific messages.
  • Behaviour: how well does the app behave? Does it send duplicates, events with wrong timestamps, or too many at once? Even the big four do some of this, so only the amount worse than them counts. Compared with: the big four's own rates for this kind of message.

How the grade is worked out

  • Each kind of message gets a score out of 100, a weighted mix of the layers that had something to check: rules 30%, fields 20%, values 20%, pairing 20%, behaviour 10%. A layer with nothing to check (no paired messages, say) is left out and the others are scaled up.
  • Findings are serious (count fully), minor (count half) or notes (shown, never counted).
  • The overall score combines the kinds of message by how many of each the app sent, so a problem in the app's busiest message type cannot hide behind many small clean ones. Kinds with fewer than 5 messages are shown but not scored; fewer than 30 count half.
  • Kinds of message the app never sends are listed but never counted: many tools send only what they are built for.
  • Grades: A 90 and over · B 80 · C 70 · D 60 · F below 60.

For the exact formulas, every parameter and every rule's definition, see the technical reference.

How to read a scorecard

  • Each app version has one scorecard, covering all its messages still on file (about six months). The four reference apps' own cards cover their last 7 days.
  • The Event types table has one row per kind of message, with its score and each layer's score. Hover over any number for how it was worked out; click a row to see the findings behind it.
  • Inside a row, each section starts with a line saying what it compares against. Findings marked not scored are notes: there for interest, with no effect on the score.
  • In the Values table each row is one field, and its Messages column counts the messages with that finding. One unusual message can appear in several rows, so the line above the table gives the number of distinct messages.
  • The Versions table at the bottom lists every version of the app with its own grade.

Common questions

Why can a message type score 100% and still list findings?
Because those findings are notes. A note marks something unusual but not wrong, such as a value outside what the reference apps happened to send recently, so it is shown and never counted.
Why isn't "outside the reference range" an error?
The reference range is the lowest and highest value in the big four's recent messages, a sample rather than a limit. A body heavier or hotter than anything in that sample is usually just a rare body. Only a gap the size of a units mistake (over 100 times the reference spread, the wrong sign, or a percentage where the reference apps send a fraction) counts. Whether a value is actually right is what Pairing checks.
Is pairing compared with a single trusted message?
No. Each place has one agreed reference record, built from all the big four's reports of it; details they disagree about are left out. Each of the app's messages is compared with that record on its own.
Why do six messages show up as eleven notes?
The Values table counts per field. A single unusual body can be outside the range in mass, radius and gravity at once, and so appears in three rows.
An app sends a kind of message the reference apps don't. What then?
It is marked "unrecognised": checked against the general rules only, since there is nothing to compare it with, and left out of the overall grade.

Limits

  • Anyone can send messages under any application name; scores describe what arrived under that name.
  • EDDN's uploader IDs change every few minutes, so nothing here can count users.
  • Scores are evidence for a closer look, not a verdict: read the findings.
