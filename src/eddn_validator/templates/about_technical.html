Technical reference

Every rule and scoring parameter as configured right now, read from config/rules.yaml and config/scoring.yaml. Rule IDs link to the lines of EDDN's documentation that state the rule, at the EDDN commit the rules were written from.

How the numbers combine

Per event type (and branch), each layer that has data scores 0–100; the event type's score is their weighted mean, with the weights of layers without data spread over the rest.

rules = 100 × (1 − Σ_rule w(severity) × failing_messages / messages_checked) floor 0 structure = mean over subtypes, by messages, of 100 × (1 − mean miss rate of expected fields) × (1 − {{ severity_weights.warning }} × share with a field no reference app sends) [journal/1 only] values = 100 × (1 − (msgs with an error finding + {{ severity_weights.warning }} × msgs with only warnings) / msgs checked) pairing = 100 × (1 − (mismatched hard pairs + 0.5 × mismatched market pairs) / pairs) behaviour = 100 × (1 − min(1, Σ max(0, app_rate − worst_reference_rate))) duplicate, stale, future, burst event = Σ weight × layer / Σ weight weights: {% for k, v in sc.weights.items() %}{{ k }} {{ v }}{% if not loop.last %}, {% endif %}{% endfor %} overall = Σ event × messages × c / Σ messages × c c = min(1, messages / {{ sc.confidence.low_below }}); event types below {{ sc.confidence.insufficient_below }} messages and unrecognised schemas are left out weak spot = an event type with {{ sc.confidence.low_below }}+ messages scoring below {{ sc.grades.C }}, flagged beside the grade grade = {% for g, v in sc.grades.items() %}{{ g }} ≥ {{ v }}{% if not loop.last %}, {% endif %}{% endfor %}, otherwise F

w(severity): {% for k, v in severity_weights.items() %}{{ {"error": "serious", "warning": "minor", "info": "note"}.get(k, k) }} ({{ k }}) {{ v }}{% if not loop.last %} · {% endif %}{% endfor %}. A message breaking several rules counts once per rule in the Rules layer, and once in the Values layer. Severity: serious when the rule is a MUST in EDDN's documentation, or breaking it leaves the data wrong for listeners, and the check is reliable; minor when the check is a heuristic, or the rule is a SHOULD or a plain instruction; note for advice, and for timing rules the behaviour layer already scores (GEN-022, GEN-023).

How pairing compares

Pairing compares what an app says about a place with what the reference apps said about the same place. One record per system, body and station is kept, built only from reference apps' messages. A message is paired only when that record exists. Every field compared counts, and one mismatch makes the message a mismatched pair.

  • System (any message with a SystemAddress): the system name must match exactly, and StarPos to within {{ pairing.pos_tolerance }} ly on each axis (positions are on a 1/32 ly grid).
  • NavRoute: the same check for every hop on the route.
  • Body (journal Scan, live game only), matched on SystemAddress and BodyID: BodyName exactly, plus each of these fields the message carries, with numbers equal to within one part in a million: {% for f in body_fields %}{{ f }}{% if not loop.last %} {% endif %}{% endfor %}.
  • Station (live game only), matched on MarketID: the name (ignoring letter case) and type, against the station as it was when the report was made (its previous name and type are kept when a reference app reports a change; a report from the stretch between the two is not compared), and only against a record from within {{ pairing.station_fresh_days }} days of the report. Also the system the station is in, at any age, when the report names the station on record (colony-era MarketIDs are reissued to other stations), except for stations that move: fleet carriers, megaships (rescue ships among them) and PowerPlay Stronghold Carriers. Colonisation's temporary stations (construction depots and colonisation ships) are not compared at all: the game reuses their MarketIDs for new stations elsewhere once a build finishes. For a station whose type is unknown, the MarketID range decides.
  • Market (commodity/3, live game only): compared with a reference app's snapshot of the same market, from the same source (CAPI or journal), taken within {{ pairing.market_window_minutes }} minutes. The set of commodities must match, and each commodity's buy and sell price.

Legacy-galaxy messages are paired on systems only, as the galaxy's stars are the same in both and everything else may differ. System, NavRoute, body and station pairs are "hard" pairs and count in full. Market pairs count half, because prices change from minute to minute.

What the gateway already rejects

EDDN's gateway checks every message against its schema (JSON Schema) before relaying it. A message with a wrong type, a missing required field or a forbidden key never reaches the relay, so no rule here checks for one. The one exception is a list the schema marks unique: the gateway now accepts a repeated item with a warning, so GEN-040 checks for it.
