{% if layer == "rules" %}

Rules: following EDDN's written rules

{{ weight }}% of each event type's score.

Compared with: EDDN's documentation, each message checked on its own.

How this layer is scored

It goes by the share of messages that break each rule, not by whether a rule is broken at all. Each rule takes off its share of messages, in full for a serious rule and half for a minor one; notes take off nothing. Rules add up, and the layer stops at 0.

Example: 10% of an app's FSDJump messages leave out the game version (a serious rule). Its Rules score for FSDJump is 90, which costs that event type {{ (weight * 0.1) | round(1) }} points ({{ weight }}% × 10). If every message left it out, Rules would be 0 and the event type would lose all {{ weight }} points of this layer.

EDDN publishes rules for how apps must prepare data before sending it. EDDN's own gateway only checks the basic layout of a message, so most of these rules are never enforced. The validator checks each message against them, one message at a time.

A Serious rule counts fully against the score, a Minor one counts half, and a Note is shown on the scorecard but never counted. A rule is serious when it breaks something EDDN says an app must do, or leaves the data wrong for whoever uses it, and the check cannot be mistaken; minor when the check is a strong guess, or the rule is advice; a note when it is worth knowing but not a fault. Each finding on a scorecard also shows how often the established apps break the same rule, for fairness.

The {{ total }} rules checked, in plain English. The technical reference lists each one's exact definition, schemas, severity weight and source, along with every scoring parameter.

{% elif layer == "fields" %}

Fields: is the expected information there?

{{ weight }}% of each event type's score.

Compared with: how often the reference apps include each field in this kind of message: their overall habits, not specific messages.

How this layer is scored

For each field every reference app always sends, the share of the app's messages missing it is averaged across those fields and taken off. In journal messages, a field no reference app sends takes off half the share of messages that carry it. Fields sent at a different rate are notes and take off nothing.

Example: a kind of message has 10 expected fields, and the app leaves one of them out of every message. Its Fields score is 90, which costs that event type {{ (weight * 0.1) | round(1) }} points ({{ weight }}% × 10).

Each message is a set of named pieces of information ("fields"): a star's type, a station's name, a system's position, and so on. This layer compares which fields an app includes with what the four established apps include for the same kind of message.

What is checked

  • ScoredExpected fields. A field is "expected" when every established app that sends this kind of message includes it in at least {{ expected }}% of them. Each expected field this app leaves out lowers the score in proportion to how often it is missing.
  • MinorExtra fields in journal messages. Journal messages accept any field, so one that no established app ever sends is worth a closer look. In other kinds of message EDDN's format already rejects unknown fields, so extras there are only noted.
  • NoteOptional fields sent at a different rate. Fields some apps send and others don't, where this app's rate differs a lot from theirs. Shown for interest.

Comparing like with like

A star scan has different fields from a planet scan, so messages are compared within groups:

  • {{ name }}: {{ what }}
    • {% endfor %}

A group needs at least {{ ref_min }} messages from an established app before it is used; otherwise the whole kind of message is used for the comparison instead, and the scorecard says so.

{% elif layer == "values" %}

Values: do the contents look right?

{{ weight }}% of each event type's score.

Compared with: a statistical profile of what the reference apps send in each field (types, known values, numeric ranges), not specific messages. The profile shifts as new reference data arrives. Whether a value is actually right for a particular body or station is checked by Pairing.

How this layer is scored

It goes by the share of messages with a problem: a message with a serious value finding takes off its share in full, one with only minor findings takes off half. Notes, such as a number a little outside the reference range, take off nothing. A message counts once, however many of its fields are flagged.

Example: 2% of an app's Scan messages send text where every reference app sends a number. Its Values score for Scan is 98, which costs that event type {{ (weight * 0.02) | round(1) }} points ({{ weight }}% × 2).

Fields can be present but hold the wrong thing. This layer looks at what is inside each field and compares it with what the established apps send in the same field.

What is checked

  • SeriousWrong kind of value. For example text where every established app sends a number, or a number where they send yes/no.
  • MinorUnfamiliar form. A value written in a way no established app writes it, such as a translated display name where they send the game's internal name.
  • MinorNumbers wildly out of range. More than {{ far }} times the spread of what the established apps report, or the wrong sign: the kind of gap that means wrong units.
  • NoteNew value in a familiar form. A star type or faction state the established apps haven't sent yet, written the same way theirs are. Elite has many rare but real values.
  • NoteNumber outside the reference range. Beyond the lowest or highest value the established apps have sent recently, but short of the "wildly" line. The range is a sample, not a limit: rare but real bodies and prices land here, so it is shown and not counted.
  • NoteDifferent capital letters from the established apps.

Which fields get a list of known values

Only fields with a limited set of possible values (fewer than {{ enum_max }}, and at least {{ enum_min }} examples from the established apps): things like star type, planet type, economy, faction state or ship name. Every value the established apps have sent over the last six months counts as known.

Never checked this way

{% elif layer == "pairing" %}

Pairing: same place, same answer

{{ weight }}% of each event type's score.

Compared with: the reference record for the same system, body or station, one message at a time. Each place has one agreed record, built from all the reference apps' reports of it; details they disagree about are left out. Six reports about the same body are six comparisons.

How this layer is scored

It goes by the share of paired messages that disagree with the reference record on at least one detail. Market comparisons count half, since prices can move between two players' visits. Messages about places no reference app has reported are not paired and do not affect the score.

Example: 200 of an app's FSDJump messages could be paired, and 10 of them give a system position that differs from the reference record. Its Pairing score for FSDJump is 95, which costs that event type {{ (weight * 0.05) | round(1) }} points ({{ weight }}% × 5).

Many players visit the same places. When an established app has reported the same star system, planet, station or market, the app's report is compared with theirs directly. This catches data put in the wrong place (for example using the previous system after a jump), rounded or damaged numbers, and mixed-up names.

Only details that do not change are compared, so reports from different days still match. Where the established apps disagree among themselves about a detail, that detail is not used.

What is compared

  • ScoredStar systems: the system's name and its position in the galaxy, for the same system ID.
  • ScoredRoute plans: the name and position of every system along a planned route.
  • ScoredPlanets, moons and stars: the body's name and its fixed details (listed below).
  • ScoredStations: the station's name and type as they were when the app reported it (stations get renamed and rebuilt, so a report from before a change is judged against the old name), if the established apps saw it within a week of the report, and which star system it is in. Fleet carriers, megaships, rescue ships and PowerPlay Stronghold Carriers move between systems, so their system is not compared. Temporary mission stations are skipped, and so are colonisation's construction sites and colonisation ships, whose ID numbers the game reuses for new stations elsewhere.
  • Counts halfMarkets: the goods on sale and their buy and sell prices, when an established app reported the same market within five minutes. Counts half, because prices can change between two players' visits.

Messages from the Legacy galaxy (the old Horizons 3.8 game) are compared on star systems only. The stars are the same in both galaxies, but planets, stations and markets may differ, and the established apps' records come from the live game.

{% elif layer == "behaviour" %}

Behaviour: how the app sends

{{ weight }}% of each event type's score.

Compared with: the reference apps' own rates for the same kind of message. Only the amount above them counts.

How this layer is scored

For each measure (duplicates, late messages, future timestamps, bursts), the app's rate minus the highest reference app's rate is taken off, if it is higher. The excesses add up, and the layer stops at 0.

Example: 6% of an app's Docked messages are duplicates, and the reference apps' highest rate is 2%. The excess is 4 points, so its Behaviour score for Docked is 96, which costs that event type {{ (weight * 0.04) | round(1) }} points ({{ weight }}% × 4).

This layer looks at sending habits rather than content. Some of these happen with every app now and then, so only the amount above what the established apps themselves do, for the same kind of message, counts against the score.

What is measured

  • ScoredDuplicates: the identical message sent again.
  • ScoredLate data: messages that reach EDDN more than {{ stale }} minutes after the event happened. Late data can be stale (a market's prices have moved on).
  • ScoredTimes in the future: a message stamped more than {{ future }} minutes after EDDN received it, usually local time mislabelled as universal time.
  • ScoredBursts: {{ burst }} or more messages of one kind in a single second, usually an app replaying old game files all at once.
  • NoteRe-sending too soon: the same message sent again 25 to 150 seconds later. EDDN asks apps to wait at least a minute before retrying.

The comparison

For each kind of message, the highest rate among the established apps is the allowance. {{ excluded }} is left out of that allowance, because it deliberately re-sends old game files when it starts, which would make the allowance too generous.
